NanoLoop

A GPT-2-sized language model that thinks in depth. A small, weight-shared transformer core is looped a variable number of times per token, so the same 61M block parameters can act like a 28-layer network, and more loops at inference buy more latent compute. Stage 2 adds continuous "neuralese" thoughts on top.

Inside every attention layer

Gated attention block, in execution order

  1. 1 · projectFused QKV, 6 heads × 128. GQA-ready via n_kv_head.
  2. 2 · QK-normParameter-free RMSNorm on q and k, softmax scale 0.12.
  3. 3 · partial RoPERotate 64 of 128 dims (base 10k). The other half are position-free content channels.
  4. 4 · value pathsV += λ·value-embed(token); V = a·V + b·V₁ (value residual from layer 1).
  5. 5 · attendSDPA / FlashAttention, causal. Sliding window when the layer is L.
  6. 6 · XSAy −= tanh(α)·projv(y). Removes self-copy; α starts at 0 (no-op).
  7. 7 · output gatey ⊙ σ(Wgx), elementwise per head; kills attention sinks.
  8. 8 · out projZero-initialised, so every block starts as identity.
  9. MLPReLU², 4× width, zero-init output.
Inference & cache

KV cache for a looping model

  1. slotsEach core layer keeps one KV cache per loop slot (iteration i → slot i mod n).
  2. early exitA token that stops at loop e copies its final K/V into the slots it skipped (Huginn latest-state sharing). Later tokens always see a valid state.
  3. exit testKL between consecutive loops' next-token distributions < ε, or relative latent change < ε.
  4. DeltaNetHybrid preset: linear-attention layers keep a constant-size state plus a 3-tap conv buffer instead of K/V.
  5. verifiedIncremental decoding matches the full forward to 1e-6 for global, sliding-window and DeltaNet layers (tests).

Stage F · frontier latent reasoning

LOTUS: a latent workspace the loop refines in parallel

inputQuestion, then the workspace⟨user⟩ Q ⟨assistant⟩ ⟨bot⟩ [Z₁,₁…Z₁,₁₃] … [Z₆,₁…Z₆,₁₃] ⟨eot⟩ #### 42
slot inputLearned, no feedbackbase + block_pos[k] + slot_pos[j]
slot targetIts own step tokenZ₁,₁…₁₀ → <<3*4=12>>, then ⟨pad-step⟩
refinementThe core loop, r ≈ 6all 78 slots updated together at every loop

Coconut (kept as a baseline) feeds thoughts back one at a time and supervises them weakly. 2026 work shows that invites shortcuts. LOTUS supervises every slot and costs one forward pass. Decoding the slots shows the model's thought trace. The eval includes a zero-workspace shortcut test and an accuracy-vs-loops sweep, as the critiques recommend (2512.21711, 2602.22441).

Stage T · tool use

Tool calling and agents: narrow, by design

  1. format<|tool_call|>{"name":…,"arguments":{…}}<|/tool_call|> → <|tool|><|tool_response|>…; calculator inline as <|calc|>48/2<|/calc|><|out|>24<|/out|>
  2. decodingNames limited to registered tools, arguments to valid JSON, over-budget arguments closed deterministically. Every call parses.
  3. loopReAct-lite, at most 3 steps; the last step must answer. Tool outputs are never trained on.
  4. dataPer-tool synthetic data (most important) + xLAM-60k (30% name masking) + Hermes FC + SmolTalk2 tool traces + no-call negatives.
  1. will workChoosing 1 of ≤20 known tools and filling a few arguments: ~90% exact match on finetuned tools. BFCL simple about 25–45.
  2. won't workUnseen tools from schema text alone, long tool outputs, error recovery, multi-step plans. Even 0.5–0.6B models score 3–4% on BFCL multi-turn.
  3. mathThe calculator removes arithmetic errors but not decomposition errors. nanochat-561M: GSM8K 4.6 → 7.6 with RL.
  4. if you need agentsUse a pretrained 0.6–1.7B base (Qwen3, FunctionGemma), with NanoLoop as a router in front.

Context length

Long context without LFM's 28T tokens

LFM2.5-350M reaches 32K because 10 of its 16 layers are gated short convolutions with a constant-size state (LFM2 report), and because it was trained on 28T tokens. loop-long copies the architecture and uses targeted training in place of the token budget.

Post-training · implemented

After pretraining: the post-training stack

At about 200M parameters, general chat ability stays modest whatever you do; numbers become real on narrow, task-finetuned targets. RL makes tiny base models worse (TinyZero, L20-Edu-135M), so rl.py measures pass@16 first and refuses to start below 30%. Every stage keeps the pretraining loop-count distribution, and rollouts and updates use the same loop count. Run eval_gsm8k.py --steps 1,2,4,6,12,24 after each stage.

Training recipe · one 24 GB GPU
  1. dataFineWeb-Edu or ClimbMix (best measured by nanochat). Validate on FineWeb to compare with the 3.28 GPT-2 benchmark.
  2. batch2¹⁹ tokens/step = 8 × 2048 × 32 accumulation
  3. budget2.5B tokens by default (~4.8k steps). Raise toward 10B for the best model.
  4. precisionbf16 autocast, per-block torch.compile, fp32 chunked loss
  5. monitorval loss at r ∈ {1, 2, 4, 6, 12, 24}: the loop is working if loss keeps falling past r=6
